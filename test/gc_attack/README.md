# GC 攻击/压力用例集

本目录收录一组**故意给垃圾回收器施加极端压力**的用例，用于：

1. 量化当前 GC 实现（分进程标记-清除 + 每轮全局标记-压缩）的成本结构与触发策略的薄弱点；
2. 在改动 GC / 分配器 / 对象布局前后做回归对比，避免性能与鲁棒性倒退；
3. 沉淀"哪些访存与分配模式会打崩 GC"的经验，供后续设计（迭代式标记、驻留表弱引用化、压缩策略、大对象区等）评估。

> **注意**：这些用例**不在 `testall.sh` / `testall_amalg.sh` 中**，也不应加进去——其中
> 有会令解释器段错误退出的（07）、有会耗尽内存池并杀死全部进程的（10）。
> 语言层面的 GC 正确性回归用例是 `test/test_gc_static_alive.scm` 与
> `test/test_strindex_weak.scm`（均已登记进两个回归脚本）。

## 运行

全部用例都只依赖内置库（`(native System)` / `(native String)`），不 `import` 模块，
因此可以在任意工作目录下运行：

```bash
./main test/gc_attack/01_baseline_churn.scm
```

参数按**桌面命令行解释器的默认 256MB 内存池**标定（heap 区初始 128MB、高水位 75%、
临界水位 90%、水位检查每 256 条指令、`AM_HEAP_COMPACT_INTERVAL=1` 即每轮 GC 都压缩）。
在 16MB 池的 `repl` 或嵌入式宿主上，需要按比例下调各文件的规模参数。

## 用例清单

| 编号 | 攻击模式 | 机制要点 | 对照 | 预期现象 | 宿主耗时 |
|---|---|---|---|---|---|
| `01` | 对照组 | 纯垃圾搅动，无大存活集合 | — | 正常结束，堆用量 1MB 量级 | ~0.2s |
| `02` | P1 高水位抖动 | 70 万个微小存活对象占堆 ~72%，垃圾一点点把水位推过 75%，每 256 条指令就触发一轮「全量标记-清除 + 全局压缩」，回收收益极小 | `01` | `heap_used` 在 92~97MB 反复横跳 | ~50s |
| `03` | 对照组 | 干净堆上反复做 2.4MB 巨型连续分配 | — | 每轮 80~110ms | ~1s |
| `04` | P2 棋盘碎片 + 巨型分配 | 交错分配只保留一半 → 空闲链表全碎块；再周期请求巨块：first-fit 扫穿链表失败、L0 边界让渡重试 4 次、碎片水位恒为级别 2 强制压缩 | `03` | 每轮 1000~2500ms（10~30 倍） | ~15s |
| `05` | P3 驻留字符串毒化（**2026-10 工单 #39 已修复**） | 长度 ≤32 的运行期字符串进 strindex；旧实现把 strindex 全量当作永久 GC 根，垃圾收不回来 | — | 修复前：堆单调上涨、每 10 万个的耗时递增、越过 75% 后近乎停滞；修复后：GC 后表项数回落到基线、堆/VM 有界 | 修复后秒级 |
| `06` | P3 计时版（**已修复**） | 同 05，每 10 万个打印累计耗时 | — | 修复前 1.0s → 3.3s → 8.3s → 15.5s（`t ∝ n²`）；修复后近似线性（100 万次约 0.55s） | 修复后秒级 |
| `07` | C1 打崩标记器 | `gc_mark` 用 C 递归遍历子对象；用循环迭代构造十万层嵌套列表（不耗 IL 栈），触发 GC 时原生栈溢出 | — | **SIGSEGV 段错误退出**（gdb 回溯全为 `gc_mark`，`rsp` 触底） | 数秒 |
| `08` | 对照组 | `09` 的搅动负载，不捕获续体 | — | 正常结束 | ~0.13s |
| `09` | P4 续体森林 | 堆中每个续体每轮 GC 都会被展开：其 opstack/fstack 在 VM 区重新分配并拷贝，全部帧闭包进根集合 | `08` | 约 14 倍耗时，`vm_used` 上涨，堆常驻 ~35MB | ~2s |
| `10` | P5 fork 放大 | 所有进程共享同一物理堆区；`fork` 深拷贝整个逻辑堆 → 对象数指数增长；任一次分配触发**全体进程**的 GC + 全局压缩 | — | 约 3 次 fork 后堆区 90%+，`[allocator] heap freelist 分配失败`，全部进程相继终止 | ~2min |
| `11` | 修复验证（规模版） | 静态字面量容器持有 20 万个运行期子列表，跨数千轮自动 GC 后逐个校验 | — | `corrupted=0` | ~5s |
| `12` | 缺陷最小复现 | 静态容器 + alive 标记残留：第 2 轮 GC 后子对象被误扫（已修复） | — | 修复前 `gc#2` 报运行时错误；修复后两次均 99 | <1s |

### 安全提示

- `07`：会段错误并可能产生 core dump，建议 `ulimit -c 0; ./main test/gc_attack/07_deepnest_mark_crash.scm`。
- `05` / `06`：工单 #39 修复后可在秒级跑完；若在修复前的旧构建上运行，默认规模会长时间无进展，可用 Ctrl-C 结束。
- `10`：会耗尽内存池并让所有虚拟机进程死亡，退出码可能非 0，属预期。
- 其余用例只做分配与回收，不会破坏宿主文件系统。

## 结论摘要（256MB 池实测）

- 单轮 GC 的成本由三部分构成：`O(全部 handle)` 的三趟扫描（`gc_root` 找续体、keepalive 扫描、sweep，每次还要在 VM 区分配 8×H 字节的键数组）、`O(存活对象 + 存活边)` 的递归标记、以及**每轮必做**的全局压缩（收集存活指针 → `qsort` → 走遍物理块 → 按 `capacity` 回写，实测约占 GC 时间 25%）。
- 因此最有效的施压方式是同时最大化「存活对象数」与「GC 触发频率」，并让每次回收的收益趋近于 0：`02`（72% 存活 + 垃圾补水位）取得 60 倍减速；`05` 在修复前（不可回收垃圾）取得累计二次增长。
- 分配器层面的两个杠杆：first-fit 的空闲链表长度（`04` 的棋盘碎片让它退化成近似线性扫描）与 `largest_request` 记账（巨块请求会把碎片水位永久钉在级别 2）。
- 两处结构性弱点会直接打崩解释器而非仅仅变慢：递归标记（`07`，原生栈溢出）与被当作永久根的驻留表（`05`，GC 无法回收）。后者已按工单 #39 改为弱驻留（GC 后按轮次戳扫尾 + 存活率压缩），`05`/`06` 由“不可回收垃圾”降级为普通分配压力。

## 生成式微基准（大字面量静态图）

`gen_static_literal_bench.py` 生成"静态图规模可调"的微基准，用于隔离测量
"每轮 GC 重新遍历静态可达图"的代价（静态字面量在进程堆中带 `static` 标志）：

```bash
python3 test/gc_attack/gen_static_literal_bench.py /tmp/gcbench 200000 40000
./main /tmp/gcbench/mb_none30k.scm        # 30000 轮 GC，无静态数据
./main /tmp/gcbench/mb_flat300.scm        # 20 万元素平坦静态字面量，300 轮
./main /tmp/gcbench/mb_nested40k.scm      # 4 万个静态子列表，300 轮
```

生成物体积较大（数十万到 1MB 量级），故不入库，按需生成到临时目录。
实测参考（同构构建、交错取中位数）：无静态数据 30000 轮共 21ms；平坦 20 万元素
300 轮 26ms → 99ms（+0.24ms/轮）；4 万静态子列表 300 轮 1791ms → 2037ms
（+0.82ms/轮）。注意该微基准的绝对值对**链接顺序/代码布局**较敏感（曾观察到
同一份源码因目标文件顺序不同而相差数倍），因此只用于同一构建配置内的 A/B 比较。
